# 三角色可配置执行与飞书话题模型切换：需求和实施边界

状态：待评审方案，尚未实施。

修订日期：2026-09-23。

适用项目：当前 Agent OS；首版按现有 macOS、飞书话题群和已注册的 CLI 验收。

本文只规定目标、边界和验收，不代表新增能力已经存在，也不授权现在安装工具、修改个人 CLI 配置、调用付费模型或发布代码。保留原文件路径，正文以本次修订为准。

## 1. 本次确定的方向

保留 CEO 助理、产品、开发三个机器人，每个角色都可以独立配置 CLI、模型和可选推理强度；三个角色都可以在飞书话题中修改本话题的模型与强度，没有话题覆盖时使用该角色的默认配置。

以下是用户的假设示例，不是固定绑定、模型白名单或已核验的 model ID：

| 角色 | 默认 CLI 示例 | 默认模型示例 | 默认强度示例 | 话题内是否可修改 |
| --- | --- | --- | --- | --- |
| CEO 助理 | Codex CLI | GPT 6 Sol | 中 | 可以，修改仅影响该 CEO 在当前话题的后续任务 |
| 产品 | Codex CLI | GPT 6 Astra | 高 | 可以，修改仅影响该产品在当前话题的后续任务 |
| 开发 | ZCode CLI | GLM 5.3 | 由用户配置或采用模型默认 | 可以，例如在需要图片时切换到经验证支持图片的模型 |

核心规则：角色决定职责和权限，配置决定执行工具，话题覆盖决定当前话题的模型选择。

本次同时收口以下要求：

1. 不增加架构机器人，技术设计由开发按需完成。
2. 不再建设“文本模型调用另一个视觉模型”的独立工具；有图片需求时，由用户切换到支持图片的主模型。
3. 不新增独立视觉 API、视觉 MCP、socket、视觉凭据或调用预算系统。
4. 图片属于可跨轮续用的任务上下文，不因一次 CLI 执行结束而要求重新上传。
5. 技术分析不自动触发用户审批；只有真正需要用户决定的事项才澄清。
6. 独立 Reviewer 必须有真实执行证据，不可用时明确报告未完成。
7. 外部能力核验和本项目实现验收分开，不能形成“先完成实现才能开始实现”的依赖。

## 3. 首版范围与不做事项

### 3.1 必须包含

- CEO、产品、开发都支持角色默认 CLI/模型/强度，以及当前话题的模型/强度覆盖。
- 配置契约覆盖项目已注册的 Claude、Codex、Cursor、ZCode；各 Adapter 按实际能力适配，不缩成只有 Codex 可配置。
- 同 CLI 不同角色、同角色不同话题之间的模型设置不串用。
- 飞书命令支持查看、设置模型、只改强度、恢复角色默认。
- 同一话题中可以在空闲且无未决流程时切换模型；是否保留原生上下文取决于 CLI 能力。
- 同任务上下文的图片可供澄清、追问、修复继续使用，必要时重新投递到所选主模型。
- 明确的普通需求可以直接交开发；独立审查、页面验证和能力失败均有验收标准。

### 3.2 明确不做

| 不做的内容 | 边界 |
| --- | --- |
| 新增长期角色 | 不增加架构、视觉或审查机器人 |
| 独立视觉转译链路 | 不做“GLM 读文字、另一个模型看图”的自动双模型调用，不新增相关服务 |
| 自动换模型 | 不按图片、任务难度或额度自动升级、降级、换供应商 |
| 话题内切换 CLI | `/model` 只改变当前 CLI 的模型/强度；更换 CLI 仍新建话题 |
| 运行中强行切换 | 不打断正在执行的任务、澄清续跑、评论修改或收尾流程来切模型 |
| 迁移未决流程 | 不把待澄清卡、待确认产品方案自动搬到另一模型会话 |
| 全量模型平台 | 不做模型市场、自动比价、所有 Provider 接入或全局费用封顶 |
| 任意新 CLI | 新增未注册引擎仍需 Adapter，不承诺只填命令名就能接入 |
| 私有状态改造 | 不修改 ZCode 私有数据库、安装包或未公开模型状态，不靠自动操作 TUI 切模型 |
| 所有需求两份文档 | 不强制产品文档和架构文档齐全才能编码 |
| 自动提取所有图片 | 不遍历产品文档内嵌图，不自动下载任意 URL，不自动跨角色传附件 |
| 全部多模态格式 | 首版只补静态图片续用，不扩展音频、视频、PDF 转图或图片生成 |
| 自动提交发布 | 不自动 commit、push、部署或创建 PR |

四个 CLI 可以分批适配、分别验收，必须公开支持状态；用户要求的组合未打通时，不能把它从范围里删除后宣称全部完成。

## 4. 角色与生命周期术语

### 4.1 职责不随模型变化

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| CEO 助理 | 判断目标是否清晰，派给产品或开发 | 代替产品澄清业务、代写代码、接管成员交付 |
| 产品 | 业务目标、范围、规则、边界、验收和 Tickets | 决定与业务无关的内部类结构、算法或数据库实现 |
| 开发 | 阅读代码、技术分析、实现、验证、独立审查后的修复 | 猜测业务规则、偷偷扩大权限、把技术选择全部推给用户 |

CEO 改用其他已支持 CLI 仍只有 CEO 职责；产品换模型不会增加派发权限；评论续接仍保持原有空业务工具权限。

### 4.2 不能混淆的五层状态

| 概念 | 含义 | 生命周期 |
| --- | --- | --- |
| 角色默认 | 配置文件里某 bot 对各 CLI 的模型设置 | 用户修改配置并按既有方式重载 |
| 话题覆盖 | 某 bot 在某 chat/topic 的模型偏好 | 用户再次设置、`/model reset` 或关闭该会话；不随一轮任务结束消失 |
| 任务上下文 | 同一所有者在同话题、同工作区里的连续工作，含需求交接材料和附件归属 | `/new`、真正切换工作区、关闭会话或选择另一段原生历史时重建 |
| 单次执行 | 一次 CLI 启动及其处理、交付和收尾 | 执行成功、失败、取消或超时后结束 |
| 原生会话 | CLI 自己的 session ID 和对话记忆 | 由 CLI 能力决定；可能在换模型时需要新建 |

同一任务上下文可以包含多次执行。“CLI 已退出”不等于“任务上下文已清空”，也不等于“待确认流程已处理完”。

建议给任务上下文增加独立 `contextId`，不要直接把 `Session.version` 当作图片归属 ID：换模型可能需要递增 version 来失效旧操作，但仍应保留同任务的图片。

## 5. 技术分析与用户确认

### 5.1 需求清楚就可以直接交开发

文案、小修复和普通功能，只要目标、范围与验收明确，都允许从用户任务消息开始；没有产品文档不构成必须回产品的理由。

开发先检查相关代码与测试；简单修改直接实现，常规功能先简述涉及模块、实施路径和验证方式，再继续编码，不额外等一次“同意”。

只有目标或业务规则确实不清楚时，才请产品整理；产品产物确认后仍由用户自行 @ 开发，不自动派发。

### 5.2 哪些情况需要技术分析

遇到并发、重试、状态迁移、新依赖、权限边界、数据迁移或多个实现方案时，开发必须先分析影响、现有约定、失败路径和验证方式。

这一步不自动触发用户确认：复用现有去重记录还是增加一个内部判断、测试如何组织、内部函数怎样拆分，通常由开发依据代码和约定自主决定。

### 5.3 只有这些未决事项交给用户

| 需要用户决定的事项 | 示例 |
| --- | --- |
| 未确定的业务行为或范围 | 重试是否允许再次向外部发送通知 |
| 新增或明显变化的费用、外部影响 | 引入付费服务、真实发消息、部署到共享环境 |
| 权限或数据暴露范围扩大 | 新角色能否访问原本不可见的数据 |
| 破坏性或难恢复操作 | 删除数据、迁移生产库、覆盖已有工作 |
| 明显用户体验或产品取舍 | 改变现有交互、放弃既有兼容性 |

确定流程：读代码并分析 → 判断是否存在用户未决事项 → 没有则自行设计并实现，有则使用现有澄清方式提问。

已经明确的范围或授权不重复询问；安全敏感操作仍遵循实际授权，不能把“做过技术分析”当成获得执行许可。

### 5.4 文档交接

- 小任务和明确普通功能可只用任务消息；常规技术思路放在开发回复里。
- 有产品文档时以其业务规则为准，技术计划不成为第二份业务需求。
- 只有用户明确需要长期保留或多轮评审时，才生成独立技术方案文档，不新增自动评论审批系统。
- 产品飞书文档与本地 Spec/Tickets 沿用现有单一交付来源规则，不自动维护两套镜像。
- 读取指定文档失败时报告缺失，不根据标题猜需求；需求变更涉及范围时再确认。
- 产品确认后自动评论修改停止，不等于飞书 ACL 已变成只读；本次不修改文档权限。

## 6. 角色默认配置与话题覆盖优先级

### 6.1 配置结构

继续使用 `config/bots.json`，保留 `defaultCli`，增加每个 bot 自己的 `modelOverrides`。

| 字段 | 含义 |
| --- | --- |
| `defaultCli` | 该角色新话题默认引擎 |
| `modelOverrides[cliId].model` | 该角色使用指定 CLI 时的默认模型 ID，接受实际 CLI 支持的 ID，不硬编码示例名单 |
| `modelOverrides[cliId].reasoningEffort` | 可选默认强度，由对应 Adapter 映射和校验 |
| 对应覆盖项缺省 | 采用该 CLI 原生默认；无效的显式值不能当作缺省 |

配置示意省略原有凭据引用、工作区和 Skills，不可直接替换完整配置；模型 ID、`medium` 和 `high` 都需按真实能力核验。

```json
{
  "bots": [
    {
      "id": "ceo-assistant",
      "defaultCli": "codex",
      "modelOverrides": {
        "codex": {
          "model": "<GPT 6 Sol 的实际 model ID>",
          "reasoningEffort": "medium"
        }
      }
    },
    {
      "id": "product",
      "defaultCli": "codex",
      "modelOverrides": {
        "codex": {
          "model": "<GPT 6 Astra 的实际 model ID>",
          "reasoningEffort": "high"
        }
      }
    },
    {
      "id": "developer",
      "defaultCli": "zcode",
      "modelOverrides": {
        "zcode": {
          "model": "<GLM 5.3 的实际 model ID>"
        }
      }
    }
  ]
}
```

### 6.2 确定的选择顺序

在开始一段新工作、没有正在续接的未决流程时，按下列顺序解析当前 CLI 的模型组合：

1. 当前 bot、chat、topic 存在话题覆盖：使用话题覆盖。
2. 没有话题覆盖：使用该角色对当前 CLI 的默认模型和强度。
3. 角色也没有配置：使用 CLI 原生默认，并显示实际模型可能未知。

例如：CEO 角色默认 Sol／中，在话题 A 设置另一个模型后，A 用话题覆盖，话题 B 仍用 Sol／中；产品和开发不受影响。

话题覆盖是一个完整的模型/强度选择，不进行隐藏的跨模型字段拼接：

- `/model set <模型ID>` 不带强度时，该模型使用 CLI/模型默认强度，不继承上个模型的高强度。
- `/model set <模型ID> --effort <值>` 同时指定二者。
- 只改强度时保留当前解析的模型选择，并将组合保存为话题覆盖；如果模型本身来源于 CLI 默认，应继续标为默认而非编造具体 ID。
- 只有 `/model reset` 清除话题覆盖、回到当前角色默认；`--effort default` 仅表示强度采用原生默认，不表示恢复整组角色配置。

实现时需区分“没有话题覆盖”和“有话题覆盖、其中强度明确采用 CLI 默认”，不能都用缺省字段而错误继承角色强度。

### 6.3 配置重载、快照与续接

- 每轮实际执行记录解析后的 CLI、模型、强度和配置来源快照；明确模型与实际模型回显分别记录。
- 已有话题的 CLI 不随 `defaultCli` 重载改变，只有新话题采用新的默认 CLI。
- 话题覆盖不受角色默认模型变动影响，直到用户 reset。
- 无话题覆盖时，新工作读取最新角色默认；如与原生会话正在使用的组合不同，按第 8 节校验切换方式，不能偷偷切换或继续用旧模型却标为新默认。
- 同一待澄清/待确认流程及其续接使用该流程开始时的有效快照，不因重载破坏进行中的工作；界面注明“角色默认已变化，当前流程结束后应用”。
- 产品评论续接采用产品会话快照与原有工具权限，不继承 CEO 或开发设置。
- 原生默认值未可核实时标为未知，不宣称系统已锁定具体模型。

角色配置、话题覆盖、执行快照和原生会话绑定分开保存，不修改全局环境变量或用户共享默认模型来模拟角色隔离。

## 7. 飞书话题中的模型命令

### 7.1 三个角色使用完全相同的命令

下列均为拟新增命令，不代表当前代码已支持；群聊中要明确 @ 一个目标机器人，不能一条修改命令同时改多个角色。私聊目标已明确时不需要额外选择角色。

| 命令 | 行为 |
| --- | --- |
| `/model` | 查看本角色当前话题 CLI、模型、强度、来源、角色默认与核验状态；只读，不调用模型 |
| `/model set <model-id>` | 设置当前话题模型，强度采用该模型/CLI 默认 |
| `/model set <model-id> --effort <value>` | 设置当前话题模型和强度 |
| `/model effort <value>` | 只改强度，保留当前解析的模型选择，并形成话题覆盖 |
| `/model effort default` | 仅将强度改为 CLI/模型默认 |
| `/model reset` | 清除该话题覆盖，按当前角色默认重新选择 |

`model-id` 是真实 CLI 标识，不是模糊自然语言别名；强度按引擎支持值校验，不假定全部引擎都接受 low/medium/high。`set`、`effort`、`reset` 为命令子项，不发送给 CLI 当作普通 prompt。

用法示意：在同一话题 @ CEO 调整其模型或强度，再 @ 产品调整产品的配置，两者互不覆盖；开发同样可以在上个任务收尾完成后设置支持图片的模型。

### 7.2 命令处理边界

- 合法 `/model` 命令由 Agent OS 确定性处理，不消耗一次 LLM 任务，也不让模型决定权限或解析参数。
- 参数缺失、多余、不认识的子命令、重复强度参数等返回用法错误；任何 `/model` 家族错误输入都不能掉入普通任务或澄清回答通道。
- 普通自然语言“换成某某模型”不能被模型宣称已完成切换；提示用户使用明确命令。
- 当前 bot 尚无话题会话时，查询显示角色默认；设置可建立仅保存偏好的空闲会话，不启动 CLI，并建立操作人归属。
- `/model reset` 在本来没有覆盖且目标未变化时是无操作，不重建会话。
- 重复设置完全相同的偏好不产生额外执行或原生上下文重置。
- 查看可以在执行中进行；修改不可以。只读展示不得泄露凭据或其他角色/话题的私有上下文。
- 模型列表自动发现、选择菜单和自然语言别名不作为首版前置条件；新模型 ID 不能仅因不在文档示例中而被拒绝。

## 8. 切换时机、原生上下文与一致性

### 8.1 谁可以在什么时候修改

修改模型、修改强度、恢复默认及其确认回调都需满足：

- 操作人符合当前会话和任务归属校验，不因为是 CEO 就能改其他人的会话。
- 没有 activeRuns 占用，没有正在执行、交付或收尾的任务，也没有另一项会话修改占位。
- 没有有效待回答澄清、待确认产品方案、正在审批的流程或已预占的排队评论。
- 会话没有关闭；操作开始和写入时的 owner、version、contextId 仍一致。

idle 只是必要条件之一，不足以证明可切换。进程重启将 active 恢复成 idle，也不自动证明业务待办已处理完。

有未决事项时默认拒绝切换，并说明具体阻塞；用户可以先完成它，或明确使用重置方式结束旧上下文。不能让 `/model` 顺便取消旧卡片。`/new` 等重置遇到未决事项时必须先明确告知影响并取得确认，不能以切换模型为名静默失效待办。

模型切换自身的待确认操作不属于阻止本次确认的“其他待办”；回调必须按操作标识排除自身，只检查其他业务流程或修改占位。等待用户确认时不长期持有执行互斥锁；用户开始新的业务执行、重置上下文或提交新的模型修改请求时，使旧切换确认失效。取消、超时或失效要释放本操作占位，不能形成无法确认也无法继续任务的循环。

无 owner 的旧会话不能因为旧保护逻辑宽松就默认授予任意人模型修改权限；首版拒绝原地修改并提示在新话题建立明确归属，不扩展为新的管理员权限系统。

### 8.2 保留飞书话题不等于保留原生记忆

各 CLI 分别核验以下能力：

| 能力结果 | 行为 |
| --- | --- |
| 能可靠改变模型/强度并保留原生会话 | 在无未决流程时更新话题选择，后续执行按新组合续接 |
| 能指定新模型，但只能通过新建原生会话实现 | 明确提示将新建 CLI 上下文，用户确认后在原飞书话题内切换 |
| 无可靠的指定模型机制 | 拒绝该选择并报告适配受阻，不猜 flag，不修改共享默认值 |

不能因为存在 `/new` 就声称能够换模型；清空原生 ID 本身没有选择模型的作用。

需要新建原生上下文时，确认信息至少包含：目标角色、CLI、目标模型与强度、配置来源、原生记忆重置、保留的需求/文档/图片范围，以及后续执行按新模型计费。用户取消确认时，所有旧设置和绑定不变。

切换保留飞书话题、工作区、已有文件和当前任务上下文的附件归属，不删除旧 CLI 历史；但不承诺复制完整原生记忆。新会话的交接只包含已保存的当前目标、已回答澄清、权威文档引用、最近交付摘要和图片清单，不自动搬运全部聊天或声称模型记得所有历史。

这些交接材料应在任务处理时保存到当前上下文；资料不足或超出可用上下文时明确列出缺失，不能让模型凭空补齐，也不另起付费模型自动总结。

### 8.3 原子修改与确认回调

- 命令先校验本地语法、引擎已知能力、权限和状态；查询能力不能启动具有业务副作用的任务。
- 需要确认时只创建待确认操作，不提前覆盖模型、清空原生 ID 或作废图片。
- 确认绑定 bot、会话、contextId、version、发起人、目标组合、操作类型、目标覆盖是否存在、配置来源和当时角色默认指纹，10 分钟失效；目标或上下文变化后不能继续使用旧确认。
- 操作类型区分“设置话题覆盖”“清除话题覆盖”“应用重载后的角色默认”；目标模型相同也不能混用：reset 必须清覆盖，默认重载必须继续没有覆盖，不能在回调中都写成固定话题模型。
- 最终写入前再次检查权限、activeRuns、其他待办/评论占位、配置指纹及本操作仍有效；同一会话的模型修改与开始任务使用同级互斥保护，检查与写入之间不能插入新任务。
- 话题覆盖的值或删除、配置来源、原生 ID 是否清空、执行快照是否失效和 version 递增作为一次持久化更新，失败恢复原状态。
- 同时到达的两次切换、重复点击和迟到回调不能相互覆盖；已应用的重复回调只返回已有结果。
- 模型切换递增 version，但不改变仍然属于同一任务的 contextId；真正重置任务才改变 contextId。

设置成功只说明选择已保存；如果尚未调用目标模型，回执写“已设置，下一次执行验证”，不能写“实际模型已验证”。命令自身校验或持久化失败时旧状态不变；设置成功后首次执行才遇到模型拒绝，则报告该选择运行失败，不能偷偷用旧模型完成任务或自动回退。

### 8.4 与现有操作的关系

| 操作 | 话题模型覆盖 | 任务上下文/图片 | 原生会话 |
| --- | --- | --- | --- |
| 普通追问、澄清回答、修复 | 保留 | 保留关联，仅校验并投递本轮需要的图片 | 按引擎续接 |
| 成功设置模型/强度 | 更新 | 同任务保留 | 按能力保留或确认后新建 |
| `/model reset` | 清除，采用角色默认 | 同任务保留 | 目标组合改变时同样走切换校验 |
| `/new` | 保留该话题偏好 | 建立新 contextId，不再自动附带旧图 | 清原生绑定；CLI 不变 |
| 真正切换工作目录 | 保留该话题偏好 | 新上下文，旧图不跨工作区继承 | 清原生绑定 |
| 取消一次执行 | 保留 | 保留，便于用户继续同任务 | 按现有取消结果处理，不伪造执行成功 |
| 关闭会话 | 结束该会话覆盖 | 结束关联，不再恢复旧图 | 不删除原生历史文件 |
| 选择另一段原生历史 | 需验证与当前选择相容 | 建立新上下文，不混入当前图片 | 仅已有引擎支持路径；不新增 ZCode 历史 `/resume` |

`/new` 清任务而 `/model reset` 清模型偏好，两者不能混用；提示文本和测试必须体现这个区别。

## 9. 图片跨轮续用与主模型原生多模态

### 9.1 唯一路线：主模型处理图片

本轮需要理解或对照图片时，用户选择一个经验证能够通过当前 CLI 接收图片的主模型，该模型负责这一段任务的理解和实现；没有独立“看图后交给另一模型”的自动流程。本轮只是纯文本工作时，不要求一直使用视觉模型。

GLM 5.3 Flash 等名称只是候选示例，必须核验实际图片能力与 CLI 输入路径。模型本身支持视觉，但 CLI 不能正确传图，也不能算该组合已支持。

发现当前模型不能处理必要图片时，报告能力限制，不虚构图片内容、不自动换模型。此类能力阻塞不创建必须先回答的业务澄清卡；本轮收尾完成且无其他未决流程后，用户可 `/model set` 切换，再继续原任务，避免陷入“等看图才能澄清、等澄清才能换模型”的循环。

若产品方案已经待确认，随后补图且当前模型不能看图，已有待确认流程仍然阻止模型切换，不能只回复“请切换模型”：

- 补图可按归属和文件规则登记，但不能声称已理解图片、已按图修改方案，也不能自动确认产品方案。
- 明确指出阻塞来自哪份待确认方案或哪项其他待办；不建议用户先确认尚未核验的方案，只为解锁切换。
- 用户可保留待办，暂不处理这项视觉变更；确实要换模型重新处理时，走显式重置确认，不自动迁移旧流程。有执行或评论正在处理时，先等收尾或按既有取消流程结束。
- 重置确认列出将失效的澄清/方案卡片和将清除的当前 contextId 图片关联，包括新补图；说明只断开关联，不删除产品文档、原图文件或代码，CLI 与话题模型偏好仍保留。
- 用户取消重置则全部保持；确认重置后，先设置所需模型，再明确提供原产品文档引用及必要原图建立新任务，旧卡片不能继续使用。此处因用户主动结束旧上下文而需补图，与正常澄清/追问不重复上传的规则不同。

### 9.2 图片归属任务上下文

最小登记信息包括附件标识、本地路径、原消息、类型、内容摘要，以及所属 bot、chat/topic、contextId、owner、工作区；可在现有持久化结构中保存引用，不新建永久图片服务。

- 同一所有者、同一角色、同一任务上下文可以在澄清、普通追问和修复中继续使用已提供图片。
- 普通执行完成、失败、取消或收到澄清卡，都不自动删除图片关联。
- 不自动按“模型说完成了”判断整个上下文结束；用户开始无关任务且不想携带旧图时使用 `/new`，话题模型偏好仍保留。
- 不同角色即使共用飞书话题，也不能自动继承对方图片；不同所有者、其他话题或工作区也不能自动共享。
- contextId 不依赖单次执行 ID，换模型引起的 version 更新不能意外断开原图关系。
- 重启后恢复已持久化引用，再校验 owner、工作区、文件存在性和内容；不是恢复已结束执行的权限或继续后台发请求。

不新增单图管理命令；首版用户要彻底停止旧图片自动续用时，以 `/new` 清空该任务上下文的附件关联。

### 9.3 持续保留图片关联，按本轮需要投递原图

普通消息、澄清回答和产品续接都可以恢复当前任务的附件索引，但恢复索引不等于向模型发送全部原图。根据当前指令、正在延续的任务目标和已确认文字材料，明确本轮是否依赖视觉，只校验并投递相关图片。

| 本轮工作 | 原图处理 |
| --- | --- |
| 按图实现、读取图中文字、重新对照页面或依赖未转成明确需求的视觉细节 | 需要原图，所选 CLI/模型必须支持图片，按原生机制传入 |
| 回答此前视觉任务的澄清，如只回复“局部”或点击选项 | 继承该任务尚未完成的视觉需求，不能仅因本条回答没有图片关键词就省略原图 |
| 按已明确的需求修改接口、算法、测试等不依赖视觉的逻辑 | 不新增图片输入，可使用文本模型；原图关联保留，不能因此标记视觉验收已通过 |
| 无法判断是否仍需读取视觉细节，且会影响范围或验收 | 只澄清这个实际缺口，不能默默按纯文本处理或猜测图片内容 |

本轮是否使用原图和选用的附件应随执行输入记录，便于核验；不增加独立分类模型或自动模型路由。文本任务不因未选用的历史图片缺失、超限或模型不支持图片而受阻，也不要求先删图。

必须验证以下黄金路径：

```text
用户 @ 开发并上传设计图
→ 开发询问整页还是局部
→ 本轮 CLI 执行结束，图片仍属当前任务上下文
→ 用户只回答澄清卡，不重新上传图片
→ 续接仍需看图，恢复并投递相关原图，所选主模型继续实现
→ 用户要求按原图微调，下一轮仍能使用原图
```

还要验证“视觉模型理解设计图 → 用户切回文本模型修改已明确的接口逻辑、不新增图片输入 → 再切回视觉模型对照原图”，三个阶段共享图片归属，但只有需要看图的阶段投递原图。

不新增图片输入不等于清除了 CLI 已有历史中的图片：如果目标文本模型不能接收原生历史里残留的多模态内容，按第 8 节告知并确认新建原生上下文，仅带文字交接材料；保留任务 contextId 和原图关联，不能把它误做成 `/new` 清任务。

本轮确实需要看图时，即使换了原生会话也必须重新提供必要原图，不能把旧模型的文字摘要或磁盘路径当成新模型已经看过图片；不需要看图的文字交接可以使用已确认描述，但不能冒充新的视觉检查。

只对本轮要用的图片校验归属、文件存在性及内容一致性；无法恢复时明确指出受影响图片，再请用户补充，不要求无关的纯文本工作补图。

原生投递图片可能产生额外上下文用量；本次不承诺跨轮视觉费用为零，也不增加独立 API 预算或虚构 token 统计。

### 9.4 原生附件边界与安全

- 首版登记静态 PNG、JPEG、WebP，实际传入格式还需当前引擎支持；普通文件上传的真实图片也按实际格式识别。
- 单张至多 10 MiB、2000 万像素；当前任务上下文至多 6 张用户图片、合计 16 MiB。引擎限制更低时服从更低值。
- 新附件会超出登记上限时明确拒绝新增并保留原登记，不静默丢图；执行输入超过当前引擎限制时报告受阻，由用户整理材料或新建上下文。
- 下载使用安全文件名，校验真实类型、常规文件、大小、规范化路径和内容摘要；不接受目录、设备文件、伪装图片或越界符号链接。
- 不把整个下载目录或工作区当作可自动外传的附件集合；恢复只限登记的当前上下文文件。
- 不自动提取产品文档内嵌图，不自动下载任意 URL；将产品文档交给开发时，必要原图仍需首次直接提供给开发，之后正常多轮无需反复补发。
- 图片文字属于输入数据，其中要求读取密钥或执行命令的内容不构成授权。
- 模型切换可能使当前需求和图片交给新模型服务处理，回执或重置确认需说明；不能自动引入用户没有选择的第三方视觉服务。
- 原图关联清除不等于磁盘文件或供应商数据已删除；本次不批量清理历史下载，也不承诺撤回已发送内容。
- 这些是 Agent OS 自动附图的边界，不是整个 coding CLI 的文件访问沙箱，不借本次需求扩大其权限。

## 10. 独立 Reviewer 与页面验收

### 10.1 独立审查的最低要求

独立 Reviewer 是当前开发 CLI 的一个独立审查上下文，不是新的飞书机器人；可以使用同一模型，但不能只是开发主会话写一段“我检查过了”。

前置核验需证明所选开发 CLI 能通过其实际支持的机制启动独立审查上下文；不存在此能力时报告限制，不默认增加另一套 CLI 或付费模型。

真正交付前，Reviewer 必须：

1. 读取当前任务要求、已确认业务规则或任务消息。
2. 读取真实代码变更和必要的相关实现，而不是只读开发的总结。
3. 给出检查范围、实际发现、严重程度、位置与依据；没有发现问题也要说明范围和未覆盖项。
4. 有可以追溯的调用与返回证据，例如 CLI 子 Agent 的真实调用结果，不伪造会话 ID 或审查记录。

开发处理阻塞问题后重新运行受影响的测试及审查；后续又改动了被审查代码，旧审查不能直接作为新版本通过证据。

模型或 CLI 更换后，审查能力要以新组合为准；“以前那个 CLI 有 Reviewer”不证明现在仍能调用。Reviewer 使用的实际模型/配置如可取得则记录，不能默认它自动继承开发主模型的所有设置。

### 10.2 失败与交付状态

- Reviewer 未安装、能力不存在、启动失败、超时或没有有效返回：标记“独立审查未完成”。
- 主会话自检、类型检查和测试可继续进行，但不能替代独立审查。
- 用户可以收到“代码已实现、测试已完成、审查受阻”的阶段结果，但不能收到“全部验证通过”。
- 不无限修复循环；遇到相同阻塞且无法取得新证据时停止并说明问题。

### 10.3 页面与图片任务的验收

需要 UI 验收时启动应用、操作真实页面并截图，由当前支持图片的主模型对照原图检查；不新增视觉工具或强制第二份设计文档。

浏览器生成截图只是第一步，还必须证明当前 CLI 将截图以图片内容交给了模型；只返回文件路径、DOM 文本或工具成功状态，均不能算模型已看见截图。

| 已核验的截图输入能力 | 接续方式 |
| --- | --- |
| 同轮工具结果或 CLI 原生读图能力可以提供图片内容 | 在当前执行中读取新截图并比较，保留实际图像输入和模型观察结果的证据 |
| 只能在执行启动/续接时附图 | 本轮登记截图并报告“待截图验收”；收尾后由用户在同话题明确继续验收，下一轮按原生附件机制提供必要参考图和该截图 |
| 两种路径都不支持或尚未核验 | 标记页面视觉验收受阻，不以截图文件存在冒充通过，不自动切模型或接另一服务 |

下一轮使用的截图必须是本任务受控截图目录中实际生成、通过归属/文件校验并登记到当前 contextId 的验收附件，记录页面状态、视口和生成时间；不能接受任意本地路径作为已授权截图，也不扫描整个工作区。登记和投递遵守第 9.4 节限制，不覆盖用户原图。

下一轮要重新验证 owner、contextId、模型能力和文件内容；上下文已经重置则不恢复旧截图。若 CLI 只能新建原生会话传图，仍遵守第 8 节确认流程，不能在上一执行尚未收尾时启动第二次执行。复查时页面或代码已变化，应重新截图，不能拿旧图验收新版本。

能力探测须让模型指出截图里可核对的具体可见信息，并保留图像传递证据；探测不能提前把答案放进 prompt 或工具文字结果，否则无法区分看图与复述文字。选择同轮还是下一轮路径由实际 CLI 能力决定，不要求同时实现两套。

记录视口、页面状态、操作结果和可定位差异；截图尺寸或状态不一致时说明比较范围，不编造相似度。实际交互、数据正确性、测试与独立代码审查仍分别验证。

无法启动应用、没有账号、浏览器能力缺失、截图未真正投递或下一轮验收尚未完成时，报告“页面验收未完成”，不能用构建通过代替。

## 11. 错误处理与用户可见反馈

| 场景 | 必须行为 | 禁止行为 |
| --- | --- | --- |
| 模型或强度格式错误 | 返回用法或校验错误，不改设置 | 将错误命令当 prompt 执行 |
| CLI 已知不支持显式选择 | 启动前说明具体能力缺口 | 静默忽略或回退默认 |
| 设置后实际运行被模型服务拒绝 | 保留清楚的请求值与失败状态，用户重新选择 | 换旧模型假装完成原请求 |
| 执行/收尾/评论排队中修改 | 明确拒绝，保留原配置 | 只看 idle 就写入 |
| 待澄清/待产品确认时修改 | 说明先处理或明确结束旧流程 | 自动失效旧卡片、迁移未决流程 |
| 需要重建原生上下文 | 先展示影响，确认后更新 | 保证完整记忆无损继承 |
| 持久化失败或版本变化 | 整次修改失败，原状态不变 | 只改模型不改绑定，留下半套状态 |
| 图片缺失或超限 | 指出具体图片和影响，相关验收受阻 | 装作已看原图 |
| Reviewer 不可用 | 独立审查未完成 | 自检冒充独立审查 |
| 用户取消执行 | 复用既有取消机制，停止后续自动执行，保留可续用上下文 | 取消后继续在后台启动新任务 |

`/model` 查询与设置回执至少显示：目标角色、话题 CLI、请求模型、强度、来源（话题覆盖/角色默认/CLI 默认）、实际值核验状态、是否需要新建原生会话。

成功设置不自动开始业务任务；用户之后发任务或继续指令才执行。实际模型回显不可取得时如实标为未核验，不把模型自述当证据。

开发交付分别报告实现、基础验证、页面验收、独立审查和剩余问题，采用通过/失败/受阻/未验证/不适用状态；成员结果仍直接通知用户，不再交 CEO 转述。

本次不新增视觉服务收费规则。费用来自所选 CLI/模型本身；没有服务端用量时记为未知，不补零，不保证取消能撤销远端计费，也不自动换账号或模型绕过额度。

## 13. 前置核验与实现任务顺序

### 13.1 T0 只核验外部能力

可以编写最小、可撤销、使用非敏感数据的探测程序；真实模型调用、费用和图片发送需获得授权。探测不需要完整 Agent OS 新功能，也不等于最终实现通过。

| 外部能力 | T0 要回答的问题 |
| --- | --- |
| 模型与强度选择 | 当前 CLI 是否有官方可用的指定机制、哪些字段支持、如何验证实际模型 |
| 新建与续接 | 指定组合能否新建、按返回 ID 续接，续接会不会恢复默认 |
| 模型切换模式 | 能否保留原生会话；如果不能，能否在同 CLI 新会话使用目标模型 |
| 原生图片输入 | 模型和 CLI 组合能否真正接收静态图片，新建/续接分别如何传入；切回文本模型时，含图片的原生历史是否要求新建上下文 |
| 独立 Reviewer | 当前开发 CLI 能否启动独立审查上下文并返回结果 |
| 页面工具与截图传入 | 能否操作测试页面并生成新截图，再在同轮以图片内容交给模型；若只能下一轮附图，用最小探测验证续接方式，模型需指出未提前写入文字输入的具体可见信息，只有路径不算通过 |
| 现有角色工具 | 所选 CLI 能否正确调用当前角色本来需要的应用工具 |

T0 不要求先实现话题覆盖数据库、模型切换确认卡、任务图片索引、原子权限检查或最终并发测试；这些属于后续实施验收。旧视觉 API、socket、视觉预算和授权重启测试已不在本方案范围。

### 13.2 实现阶段无循环依赖


自动测试覆盖解析、优先级、角色/话题隔离、持久化、并发、权限、版本、图片上下文恢复、按需投递和错误行为，并包含待确认方案补图后拒绝切换及重置影响确认；默认测试不消耗真实模型额度。

真实验收使用经授权的非敏感任务，覆盖三角色话题修改与 reset、实际所选模型新建/续接、跨轮原图恢复、视觉→文本→视觉且中间不新增图片输入、需要重建原生会话的切换，以及独立 Reviewer/实际页面验证。页面证据必须覆盖新截图真正进入模型的已选路径，不能只有截图文件；引擎没有某项能力时如实列为未完成或不支持，不用 mock 通过冒充实际可用。

回归原有角色工具、产品确认/评论互斥、普通附件、取消/超时、命令处理及四种 CLI 原有路径；未使用图片的任务不能因为某模型缺视觉而整体不可用。

完成条件：本次范围与用户实际选用组合有对应证据，T0 外部能力和各实施阶段分别通过，没有把受阻项改成默认值来规避验收，没有把未执行的审查/页面检查写为通过。

## 15. 交给开发前的选择与本版结论

| 事项 | 需要明确的内容 | 没有确定时可以做什么 |
| --- | --- | --- |
| 初次使用的角色默认值 | 各角色实际 CLI、model ID、可选强度；示例不是永久选型 | 实现配置结构和本地测试，不写死示例模型 |
| 图片任务所选主模型 | 该模型和 CLI 是否真正支持图片 | 做原生能力探测与本地图片归属测试，不假定 Flash 必然可看图 |
| CLI 存在适配限制 | 用户决定换成已支持组合、等待适配，或主动采用原生默认 | 保留需求并报告阻塞，不擅自更换模型 |
| 真实外部调用 | 使用现有 CLI 账户的模型费用与任务图片发送授权 | 只运行本地测试和只读能力检查 |

本版不再要求用户选独立视觉 API 或为它提供密钥；模型切换只影响用户指定角色的当前话题，没有覆盖时使用角色默认。

优先实现角色配置和三角色话题模型命令，再接好跨轮材料与图片，最后完成工作流、Reviewer 和真实页面闭环；这是实施顺序，不是新增四轮人工审批。
