# 协作流程恢复与配置迁移

- 代码审查在开发 CLI 内部完成（`implement-ticket` 调用 Code Reviewer Sub Agent），Agent OS 不再另开审查会话，也没有 `reviewBy` / `reviewMaxRounds` 配置；旧配置里的这两个字段会被忽略。
- 普通产品问答不会触发方案提交；只有实际调用 request_spec_approval 才会生成确认卡。
- 产品方案确认即流程终点：无论方案来自用户直接咨询还是 CEO 派发，确认只保存记录，不会自动交回 CEO 或派给开发。需要实现时由用户自行 @ 开发并附上文档。协作成员完成任务后直接通知用户，不再回传派发方。
- 所有非 Leader 成员都可以调用 request_clarification 发起选择卡；Leader 只能派发。
- 评论修改仅允许原任务发起人请求。排队或执行评论期间不能确认；确认后禁止继续评论修改。其他协作者的建议应由发起人确认后转交。
- 任务身份优先比较同一开发商范围内的 union_id。缺少 union_id 时，只允许在原应用内比较 open_id；跨应用无法识别时拒绝操作，不猜测身份。

## 持久化与重启

`data/clarification-flows.json` 保存澄清问题及已选答案；继续执行失败会显示“重新整理”按钮，已选答案不会清空；也可在话题补充。`data/product-spec-flows.json` 记录方案待确认 / 已确认 / 已失效状态。`data/collaboration-inbox.json` 保存尚未消费的派发与去重记录。

网络失败后不会撤销用户的确认。启动后及每分钟补发尚未送达的协作派发（例如目标 Bot 当时离线），使用原 dispatchId 防止重复执行。发送结果不确定时可能再次发出通知，但已消费的派发不会再次执行。单进程运行；不要让两个 Agent OS 进程共用同一 data 目录。执行中进程崩溃的 CLI 任务不会自动重跑，以免重复外部副作用；需要用户检查后继续。

内存协作记录保留最近 1000 条，持久化消费去重记录保留最近 10000 条；产品历史保留最近约 1000 条终态记录，仍在等待确认的方案不会清理。待派发达到 1000 条时拒绝新增并提示处理积压。

## 飞书评论接入

产品默认通过用户身份创建文档，运行中的 Bot 使用应用身份订阅和回复评论。需要给对应 Bot 开通评论事件及读取、回复权限，并让该应用能够访问目标文档或 Wiki 节点；用户 CLI 授权不会自动赋予 Bot 权限。订阅失败只禁用评论监听，聊天和确认功能继续工作。修正权限后重启以重新订阅。

提交链接仅接受 HTTPS 的 feishu.cn / larksuite.com Docx 或 Wiki 地址。Wiki 在提交时解析为原始 Docx；权限不足会明确报错，不生成虚假确认卡。工作区产物路径会同时检查 Windows 绝对路径、路径穿越和符号链接逃逸。

## Windows

不再通过 shell 拼接 CLI 参数。原生 exe 直接启动，标准 npm cmd 启动器解析到 Node 入口运行；未知自定义批处理会明确拒绝，并提示安装官方 npm 版本。这样包含空格、中文、JSON 和 shell 元字符的参数不会被 cmd 再次解释。

## 提交范围
