# 架构设计（arch-design）

## 何时使用

- 需求复杂（跨模块、涉及数据模型/迁移、外部系统集成、性能或安全权衡）或用户明确要求架构设计时，**先产出架构设计**，经用户确认后再进入实现。
- 小改动、单点修复、明确的配置调整**不强制**产出架构文档：直接实现并交付，不要为了流程生成文档。

## 输入

- 已确认的产品方案（PRD）：用户在已确认 PRD 卡片上点击「转架构设计」后，会得到一段**架构交接码**（32 位十六进制，单次有效）。把交接码随任务一起带来，提交架构设计时原样使用。
- 不要自报产品方案编号、文档 URL 或任何编造的上游信息充当交接码；没有交接码就先请用户在已确认的产品方案卡片上发起架构交接。

## 产出结构

架构设计文档（本地交付时为单个 Markdown 文件，如 `.scratch/<feature>/architecture.md`）必须包含：

1. **模块划分**：模块边界、职责、依赖方向；复用/新增/删除的模块分别列出。
2. **接口契约**：模块间与对外的关键接口（签名、错误语义、幂等/重试约定）。
3. **数据模型与存储**：新增/变更的实体、索引、约束；兼容旧数据的说明。
4. **迁移方案**：数据迁移、灰度/回滚步骤与失败处置。
5. **风险与权衡**：主要技术风险、被否决的备选方案及理由（不虚构未评估的方案）。
6. **测试方案**：单元/集成/验收测试的层级与关键用例（对齐 PRD 验收标准）。

引用多系统业务知识时，只使用上游 PRD 继承的知识引用范围（`[[kb:...]]` 令牌格式），引用不可解析时显式标注，不得编造。

## 提交与边界

- 交付完成后调用 `request_architecture_review`：本地交付提交 `deliveryMode=local` 与 `designPath`；飞书交付提交 `deliveryMode=lark-doc` 与文档 `documentUrl`；`handoffToken` 使用用户提供的架构交接码。
- 架构确认与编码授权是**分开的状态**：架构确认前不要开始编码；架构确认也不等于允许开发，实现仍需用户单独发起。
- 不要向 issue tracker 或任何外部系统发布架构内容；不要在提交前对外声称架构已获批准。
